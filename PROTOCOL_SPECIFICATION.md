# Sibna Protocol Specification

This document provides a technical overview of the implementation details of the Sibna Protocol.

## 1. Key Agreement: X3DH

Sibna implements the Extended Triple Diffie-Hellman (X3DH) protocol for establishing shared secrets between two parties.

### 1.1 Key Types

- **Identity Key (IK)**: A long-term Ed25519/X25519 key pair.
- **Signed Prekey (SPK)**: A medium-term X25519 key pair signed by the Identity Key.
- **One-Time Prekey (OPK)**: A single-use X25519 key pair.
- **Ephemeral Key (EK)**: A fresh X25519 key pair generated by the initiator for each session.

### 1.2 Key Derivation

The shared secret is derived through four Diffie-Hellman operations (DH1–DH4) combined using HKDF-SHA256. Domain separation is enforced using version-specific constants (e.g., `SibnaX3DH_SessionKeys_v9`).

### 1.3 Post-Quantum Hybrid Handshake (Default: ON)

**The `pqc` feature is enabled by default.** Every handshake is a hybrid of two independent key-exchange mechanisms:

1. **X25519**: Classical Diffie-Hellman (as in standard X3DH).
2. **ML-KEM-768** (CRYSTALS-Kyber, FIPS 203): The initiator encapsulates a secret against the responder's ML-KEM public key.

**Key Fusion**: The classical DH and post-quantum KEM shared secrets are **concatenated** before being passed to HKDF. This means:
- The session key is secure as long as **either** X25519 **or** ML-KEM-768 remains unbroken.
- A quantum adversary must break **both** primitives simultaneously.

> **⚠ X25519 alone is NOT post-quantum secure.**
> If the `pqc` feature is disabled (`default-features = false`), the handshake falls back to classical X25519 only, which is vulnerable to Shor's algorithm on a sufficiently capable quantum computer.

## 2. Session Management: Double Ratchet

Once a shared secret is established, the Double Ratchet algorithm manages message encryption.

### 2.1 Symmetric-Key Ratchet

Every message is encrypted with a unique key derived from a chain key. The chain key is updated via HMAC-SHA256 after every message, providing forward secrecy.

### 2.2 Diffie-Hellman Ratchet

A DH ratchet provides post-compromise security. Every few messages (or upon a role swap), new DH keys are exchanged to reset the security state.

---

## 3. Group Messaging

Group sessions use the Sender Key pattern:
- Each participant generates a chain of keys (Sender Key).
- The Sender Key is distributed to other group members via pairwise 1:1 sessions.
- Group members use the shared Sender Key to decrypt messages from that specific sender.
- Maximum skipped messages are limited to 500 to prevent memory-based DoS attacks.

---

## 4. Cryptographic Primitives

| Primitive | Algorithm |
|---|---|
| KDF | HKDF-SHA256 |
| AEAD | ChaCha20-Poly1305 |
| Key Exchange | X25519 (+ ML-KEM-768 by default) |
| Signatures | Ed25519 |
| Post-Quantum KEM | ML-KEM-768 (FIPS 203) |
| Randomness | OS CSPRNG via `getrandom` |
| Comparison | Constant-time (MAC & AEAD tag) |

---

## 5. Memory Management

All sensitive data structures (private keys, shared secrets, chain keys) implement the `ZeroizeOnDrop` trait. Key material is overwritten with zeros when the object is dropped from memory.

---

## 6. Out-of-Scope Properties

The following properties are **not provided** by this protocol and must be handled at a higher layer:

| Property | Status | Notes |
|---|---|---|
| Deep Metadata Protection | ⚠️ Partial | We use **PaddingMode** for packet sizes, but source/destination IPs and timing are visible without proxies |
| Anonymity | ⚠️ Partial | Native anonymity achieved **only** via configuring `P2pConfig::proxy` for SOCKS5/Tor routing |
| Automated MITM Prevention | ⚠️ Partial | `verify_or_pin_peer_key` pins peer identities to prevent key drift, but TOFU rules apply on day one without manual Safety Verification |
| Transport Security | ❌ Not provided | Application must provide TLS or equivalent if not using Tor payloads |
